# IMS 0.8.0 — Retrieval Control Plane

IMS 0.8.0 changes retrieval from a single global candidate competition into an evidence-driven control loop. The objective is not to make one regression question pass; it is to reduce systematic failures where relevant source material exists but never reaches answer synthesis.

## Design invariant

A downstream LLM cannot repair evidence it never received. For that reason, 0.8.0 treats retrieval quality and evidence coverage as gates, not as incidental scores.

```text
question
  -> semantic evidence plan
  -> source policy
  -> priority-source stage (when configured/selected)
  -> goal-specific hybrid retrieval
  -> section navigation
  -> goal-local reranking
  -> evidence-satisfaction audit
       -> if incomplete: materially different search-only repair
       -> retry inside priority scope
       -> if still incomplete: broaden only unresolved goals
  -> claim/coverage-aware synthesis
  -> verification
```

## 1. Semantic planning for ordinary natural-language questions

The deterministic parser remains useful for literal identifiers and simple structural cues, but multi-word natural-language questions can now use the fast semantic planner even when they are not obviously multi-hop.

Planner output is an evidence plan, not an answer. It identifies atomic goals such as definition, responsibility, temporal rule, condition, exception, comparison or relationship. Every goal has a `coverage_contract` describing what constitutes completion:

- `single_fact`
- `all_supported_variants`
- `enumerate_set`
- `ordered_procedure`
- `all_requested_entities`
- `relationship_proof`
- `conditional_rule`
- `calculation_inputs`
- `compare_variants`

Search queries generated by the planner are explicitly **SEARCH-ONLY hypotheses**. The planner may hypothesize likely section-heading vocabulary, role/function terminology, governing concepts, procedural nouns and synonyms, but those hypotheses can never be presented as facts unless retrieved evidence supports them. New numeric thresholds, acronym expansions, technical identifiers, places and factual outcomes remain blocked.

## 2. Real priority-source retrieval

`PRIORITY_DOCUMENT_PATTERNS` identifies administrator-configured source families by title/filename. If it is empty during an upgrade, 0.8.0 inherits the existing `OVERVIEW_DOCUMENT_PATTERN` so an existing deployment does not need an immediate `.env` rewrite.

When a priority source exists, it is searched in its own stage. Its candidates do not compete with the whole corpus before the evidence-quality gate.

If every required goal is supported, Auto stops and answers. If a required goal is missing/partial, IMS first runs a targeted retrieval-repair pass inside the priority source. Only after that remains incomplete may Auto search the wider corpus, and only for unresolved goals.

Explicit `document_ids` remain a hard user scope and are never silently broadened.

## 3. Purpose-built retrieval lanes

A single natural-language string is no longer the only representation used by all retrieval mechanisms.

### Dense lane

Uses the semantic formulation as before.

### Precise lexical lane

Retains PostgreSQL `websearch_to_tsquery` for high precision.

### Relaxed lexical lane

Creates a separate OR-based recall probe from content-bearing query tokens after removing request grammar. It does not add domain terms. This prevents one missing surface word from collapsing lexical recall while keeping the precise lane intact.

### Section-navigation lane

Uses the existing `chunks.search_vector`, `section_path` and `contextual_text` to identify likely document sections. One anchor per logical section is preserved and can be expanded to neighbouring chunks in that section. No re-OCR, re-chunking, vector migration or new section table is required in 0.8.0.

### Exact/lookup lanes

Remain for literal phrases, technical identifiers and acronym definitions.

### Table lane

The extra table-specific boost is no longer applied indiscriminately. It is enabled for structurally tabular requests such as enumerations, comparisons, calculations, schedules, limits, durations, locations and similar attributes. Ordinary responsibility/relationship questions can still retrieve a table through dense/lexical search, but tables no longer receive a gratuitous dedicated boost.

## 4. Goal-local reranking

For compositional/evidence-goal retrieval, candidate scoring is performed against each goal independently before fan-in. Required goals receive bounded reserve capacity, preventing a high-scoring branch from crowding out a weaker but necessary branch.

`Candidate.goal_rerank_scores` records per-goal cross-encoder scores for auditability.

## 5. Evidence-quality gate

Candidate presence is not proof. The semantic evidence auditor sees only retrieved evidence and must decide whether each evidence goal is supported, partial, missing or contradicted.

Coverage contracts are enforced conservatively. For example, a definition using `all_supported_variants` is not deterministically declared complete just because one definition-like passage was retrieved. Enumerations/procedures/comparisons similarly require semantic coverage assessment.

## 6. Retrieval repair

If required evidence is incomplete, the retrieval-repair controller receives:

- the original user question;
- unresolved evidence goals;
- queries already attempted;
- the best retained corpus snippets/headings.

It is required to produce a materially different retrieval strategy rather than another tense/plural/word-order paraphrase. Search-only hypotheses can use conceptual, role and heading terminology. New numbers and technical identifiers are filtered out.

When a recovery call suppresses the base query, repair probes are inserted **before** seed queries so the bounded query budget cannot truncate away the new strategy.

## 7. Broaden only missing goals

After a priority stage, broad-corpus retrieval targets only unresolved required goals. Evidence already established in the priority source is retained and does not need to compete again with hundreds of unrelated candidates.

Explicit Research mode remains intentionally broader because the user requested research rather than bounded Q&A.

## 8. Observability

`query_logs.retrieval_trace` now carries additional fields including:

- `source_policy`
- `source_stage`
- `priority_stage`
- `priority_stage_complete`
- `priority_recovery_attempted`
- per-query origins/goal attribution
- relaxed/section source counts
- goal-local reranking details
- per-goal rerank scores
- goal satisfaction / missing / partial / contradicted IDs
- retrieval repair queries and timings

This makes it possible to distinguish planning failure, source-routing failure, candidate-recall failure, reranking loss, evidence-selection loss and answer-generation failure.

## 9. Security and ACLs

Every new retrieval lane uses the existing `document_access_clause` through `_base_filters`. Priority routing selects only documents the current user can access. Search hypotheses are never evidence and never bypass ACLs.

## 10. Upgrade/corpus impact

0.8.0 does **not** require:

- PostgreSQL migration;
- document re-ingestion;
- OCR rerun;
- re-chunking;
- re-embedding;
- inference-model rebuild.

Section navigation is built over existing chunk fields. The change is primarily API/workflow/retrieval logic.

## 11. Known boundaries

No retrieval architecture can prove an unrestricted corpus-negative assertion from ordinary top-k retrieval. IMS must still use exhaustive/source-inventory workflows for statements such as “no document contains X.” Likewise, poor source extraction cannot be fixed by query planning; a likely page with corrupt text still requires targeted visual/OCR fallback.

0.8.0 is designed to make failures diagnosable and bounded rather than to claim that every arbitrary question is guaranteed correct.
